No simulation, bootstrap, or threshold-selection run was performed for this update. The original confirmatory results and bootstrap outputs were not changed.

### Why M4 coverage repeats across target settings

The saved per-seed records show that, within each seed, the M4 `(locked_tau, locked_delta)` pair is identical at target settings 0.30, 0.50, and 0.70. The saved pairs are the same for clean and faulted conditions:

| Seed | M4 tau | M4 delta |
|---:|---:|---:|
| 202 | 0.90 | 0.00 |
| 303 | 0.90 | 0.00 |
| 404 | 0.90 | 0.00 |
| 505 | 0.90 | 0.00 |
| 606 | 0.10 | 0.15 |
| 707 | 0.90 | 0.00 |
| 808 | 0.90 | 0.00 |
| 909 | 0.90 | 0.00 |
| 1010 | 0.70 | 0.00 |
| 1111 | 0.90 | 0.00 |

Applying the same per-seed thresholds to that condition's test records explains the repeated accepted counts: 424 clean and 305 faulted at each target. The inspected target-evaluation code creates an M4 model for each target and calls `tune_thresholds_for_target_coverage` with the target value. That method searches candidate threshold pairs for validation coverage closest to the target, breaking equal-distance ties by validation selective risk. The run helper constructs train, calibration, and validation features with faults disabled, then applies the condition-specific faults to test records.

The saved results do not include per-target validation coverage, the candidate-grid scores, or selected tuning diagnostics. Thus the saved evidence shows exactly **which thresholds repeat** and why the repeated thresholds lead to repeated test coverage, but it does not establish **why the validation tuner selected the same pair for all three targets**. That selection explanation remains unresolved. The configured M4 candidate lists also are not passed by the target-tuning call; the tuner uses its own function defaults. This is a source-level configuration distinction, not proof of the cause of the repeated selection.

### Faulted 70% infeasibility label

Both original reports and the inspected bootstrap/reporting source label the faulted 0.70 setting infeasible and state an approximately 61.5% maximum-coverage ceiling. The inspected source hard-codes that label and explanation for this row; it does not derive feasibility from saved validation results. Saved test records show 101 M4 diagnostic vetoes among 520 faulted records (19.42%), while default M4 coverage is 79.42%. These saved test counts do **not** substantiate the stated 61.5% ceiling. The 70% target was not achieved on held-out faulted test data (58.65% coverage), but that alone does not establish a structural ceiling or validation infeasibility. Treat the infeasibility label and ceiling as unsupported by the available artifacts; do not replace them with another claimed bound.

## Bootstrap interpretation and unresolved details

- The bootstrap source uses `(seed, event_id)` as a physical-episode cluster and resamples seeds, then source-class episode clusters. Each cluster retains competing model predictions and both condition records, preserving the stated pairing structure.
- Primary point estimates in the independent audit agree with the raw prediction counts. The saved default risk-difference intervals use 1,000 valid replicates. These are descriptive hierarchical-bootstrap intervals with only ten seed clusters, not a formal hypothesis-test decision.
- A paired bootstrap does not make M3 and M4 accepted sets identical. Each selective risk is conditional on that method's own accepted predictions; the risk difference is not a matched-accepted-case comparison.
- In the inspected bootstrap source, M4 abstention/fault co-occurrence uses M4 decisions. This corrects the earlier review statement that the current expression used M3 decisions. The saved faulted M4 value is 107/107; the exact runtime source revision remains unknown because source provenance was not recorded.
- The bootstrap JSON's `denominator` field for a risk difference is populated with M4's accepted count. A difference of two conditional risks has no single ratio denominator; this metadata field should not be interpreted as one. The source computes intervals from bootstrap risk-difference values.
- Clean M4 fault-diagnostic precision is unavailable: all 1,000 saved bootstrap replicates are undefined for this metric. Other zero-denominator metrics remain explicitly undefined rather than coerced to zero.
- Target-setting intervals describe the locked thresholds and achieved test results. They do not establish matched-coverage effects. The faulted 0.70 feasibility status is unverified from saved validation data.

## Research interpretation and limits

The defensible conclusions are descriptive findings for the specified ten-seed synthetic benchmark, its 1D ADE setup, and the configured sensor fault suite (stuck value at `sensor_002` plus 10% random missingness; telemetry delay disabled). There are only ten seed clusters. The default pooled points do not favor M4 on selective risk, and the target-setting results do not compare M3 and M4 at matched achieved test coverage.

Do not claim M4 reduces selective risk, is superior at matched coverage, or is validated for real-world Noyyal conditions. The data do not establish field performance, regulatory suitability, or robustness to fault modes not represented in this synthetic suite.
